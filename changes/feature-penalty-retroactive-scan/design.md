# 惩罚规则追溯扫描功能设计 (feature-penalty-retroactive-scan)

## 需求理解
管理员在新建或编辑惩罚规则时，由于改变了规则条件（例如从迟到3次触发改为迟到2次触发），希望能“向前追溯”，找出过去一段时间内符合新阈值的违规记录，并对这些用户实施惩罚。

## 存在的问题分析与设计调整方案

### 当前实现的缺陷分析
在此前的初步实现中，我们将扫描的最小维度设定为了“单次预约(Reservation)”，通过前端向后端请求全量预约数据，并单条判断是否违规，从而补录「单次违规记录(Violation Record)」。
**这不符合既有的系统架构逻辑，也不满足真实需求：**
1. **重复生成记录**：当前后端在订单结单时，本来就会自动生成 `violation_records`（只要发生了迟到、爽约等），针对一次预约重复录入违规记录会导致数据不一致和膨胀。
2. **错位的核心维度**：真正的惩罚判定（`evaluatePenaltiesOnViolation`）是基于「用户（Student）」以及「统计周期内的违规次数/时长（Threshold）」的。如果我们的追溯只定位到“单次违规”，那么对于类似“30天内迟到3次才处罚”的规则，就无法通过列表呈现给管理员哪些用户满足了这3次。

### 重构后的设计方案：基于规则阈值与周期进行用户的“惩罚模拟下发”

**1. 模拟评估 API 设计**
新增一个专用的后端路由 `POST /api/admin/penalty-rules/simulate`：
* **入参**：携带前端表单中正在配置的 `trigger_config`（触发条件）、`action_config`（惩罚操作）以及追溯的时间范围（StartDate, EndDate）。
* **处理逻辑**：后端遍历系统内所有用户，使用传入的自定义规则参数，结合数据库中现有的真实 `violation_records`，直接运行现有的 `evaluatePenaltiesOnViolation` 核心逻辑进行模拟评估。
* **出参**：返回一份“满足此新规则，即将面临惩罚”的**违规用户名单 (含涉及的具体 Violation IDs 列表与统计数据)**。

**2. UI 交互流（桌面端平铺 / 移动端叠加抽屉）**
* **触发入口 (主 Drawer)**：在配置完规则后，点击新面板的“扫描符合该规则的历史用户”按钮。
* **次级 Drawer (ViolationsPreviewDrawer)**：
  * 在桌面端：由于屏幕宽度足够，第二个 Drawer 以平铺的方式显示在第一个 Drawer 左侧，不会遮挡屏幕。
  * 列表呈现：展示被扫出满足阈值的用户列表（例如：张三，迟到3次/累计迟到60分钟）。
  * 交互：管理员勾选需要对其正式下发惩罚的用户，并点击确认。

**3. 数据提交策略 (批量下发惩罚)**
将原本构思的去写 `violation_records` 改为直接写 `user_penalties`。
当在上层 Drawer 确认保存规则且包含选中的人员后：
* 调用新建好的 `POST /api/admin/penalties/batch` 接口。
* 后端收到这批用户的 ID 以及涉及的 `violation_ids` 集合后，利用新建或修改的规则 `rule_id`，利用 Transaction 批量向 `user_penalties` 插入惩罚数据。
* 完成后，受罚用户的账号将立即受到规则设定的限制（比如拉黑 7 天）。
