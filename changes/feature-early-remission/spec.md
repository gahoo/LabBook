# 赦免/提前解封 (Penalty Remission) 设计方案

## 方案选型与思路分析

### 1. 术语选择
相比 `Pardon`，使用 `Remission` (减刑/宽恕) 或 `Waive` (免除/豁免) 在业务语境下更加准确专业。我们在后续代码和数据库命名中将统一使用 `waiver` 或 `remission`。

### 2. 为什么动态惩罚没有 `user_penalties` 的 ID？
当前系统中，**动态惩罚（Dynamic Penalties）是“即时计算（On-the-fly）”的**。
每次用户尝试预约时，系统会实时聚合其在时间窗口内（如近30天）的违规记录。如果达到阈值，就直接拦截。因此，动态惩罚在数据库中**根本不存在**实体记录，自然也就没有 ID 可供关联。这就是为什么之前必须依赖记录关联的 `violation_ids`。
**补充：** 对于固定惩罚（Fixed Penalties），它们确实会在 `user_penalties` 表中产生实体记录。在我们的最终设计中，可以在豁免表中增加一个 `user_penalty_id`（允许为空）的字段。这样如果是固定惩罚，既可以记录快照，又能物理关联到被豁免的具体惩罚记录，便于后续审计。

### 3. 分析思路：将动态惩罚也写入 `user_penalties` 表并增加 `waived` 状态
**工作原理：**
当动态惩罚触发时，像固定惩罚一样，在 `user_penalties` 插入一条记录。管理员点击豁免时，将该记录的 `status` 改为 `waived`。

**优缺点与不良影响分析：**
- **优点**：数据模型统一，前端和管理员查询受限名单时直接读取一张表即可。
- **致命缺点 1（状态同步的噩梦）**：动态惩罚的结束时间是“动态”的（随着时间推移，旧的违规记录会滑出30天的时间窗口）。如果持久化到表中，系统必须依赖高频的定时任务（Cron Job）去不断扫描并清理那些“已经因为时间推移而自然失效”的动态惩罚记录。一旦定时任务延迟或挂掉，用户会被错误地永久封禁。
- **致命缺点 2（无法应对新违规 D）**：就像您敏锐指出的，如果只是把状态改为了 `waived`，当第二天用户产生了新的违规 D 时，系统检查到该规则已经有一条 `waived` 的记录，是该忽略它还是重新惩罚？如果要重新惩罚，系统依然必须知道“之前的 `waived` 是针对 A,B,C 的，现在的 A,B,C,D 是新状态”。**所以即使写入 `user_penalties`，依然逃不掉要记录 `violation_ids` 的宿命。**

### 4. 釜底抽薪的优雅方案：“违规状态快照豁免” (State Snapshot Waiver)
正如您所说，不用复杂的 JSON，直接用逗号分隔的字符串（如 `",101,102,105,"`）即可，并且**使用哨兵逗号**。

**核心逻辑：**
1. **新建豁免记录表 `penalty_waivers`**：
   字段：
   - `id`: INTEGER PRIMARY KEY AUTOINCREMENT
   - `student_id`
   - `rule_id`
   - `violation_ids`: 排序后并在首尾加上哨兵逗号的字符串，例如 `",101,102,105,"`。**使用哨兵逗号的好处**：虽然在触发时我们做的是字符串的绝对相等比对（`===`），但如果未来需要进行 SQL 统计（例如“查询包含违规ID为102的所有豁免记录”），使用 `LIKE '%,102,%'` 可以实现绝对精准的匹配。如果不加哨兵逗号，`LIKE '%102%'` 就会错误地匹配到 `1102`。
   - `user_penalty_id`: 可选，针对固定惩罚，记录具体被豁免的物理惩罚记录ID。
   - `created_at`: 豁免记录创建时间
2. **豁免的本质是“豁免某个特定的违规组合”**：
   当导师求情，管理员点击【豁免】时，系统将当前触发该惩罚的违规 ID 排序后存入表，例如 `",101,102,105,"`。
   如果是固定惩罚（Fixed），同时将 `user_penalties` 中的对应记录标记为 `status = 'waived'`（使其物理失效），并将 `user_penalty_id` 填入快照表。
3. **完美解决“第二天产生违规 D”的问题**：
   第二天用户新增违规 D（ID：108）。
   系统实时计算（或触发检查）时，获取到当前的违规组合是 `",101,102,105,108,"`。
   拿着这个新字符串去 `penalty_waivers` 匹配，发现没有匹配项（因为只豁免过 `",101,102,105,"` 这个历史状态）。
   **于是惩罚立刻重新触发！**
   这就完美实现了：导师求情只能保你这一次（基于过去的违规），一旦你再犯，旧账新账一起算，瞬间重新封禁！

这个方案既保留了动态惩罚的“无状态、实时计算”的高性能优点，又用极简的字符串匹配完美解决了“豁免后复发”的棘手问题。
