# Reservation 模块重构与极限测试规范 (Specification)

## 1. 目标与背景
Reservation（预约模块）是系统中最核心、状态流转最复杂的部分。为了在物理剥离代码时不引入任何回归问题，必须遵循严格的 TDD（测试驱动开发）流程。在修改业务代码前，先建立一张致密的“极限测试网”。

## 2. 测试策略：六大维度极限测试网 (基于审查建议升级)
基于同行 AI 的审查反馈，必须消灭“假阳性”断言，并补全生命周期状态流转漏洞。

### 一、基础参数与边界校验 (`POST /api/reservations`)
- **必填项与格式**：空值、非字符串、字符溢出、非整数的 400 拦截。
- **硬编码强拦截**：导师包含“教授/老师”时的拦截；邮箱后缀白名单拦截。
- **时间极性边界 (升级)**：测试早于当前时间、非法日期格式，以及**结束时间早于/等于开始时间 (`end_time <= start_time`)** 的拦截。

### 二、设备规则与惩罚降级引擎 (核心深水区)
- **时长下限/每日上限**：`< minDuration` 及单日累计超额拦截。
- **惩罚动态降级 (修复)**：
  - `REQUIRE_APPROVAL` 处罚：**必须**在判断返回值为 200/201 的前提下，再去数据库断言状态确实变为了 `pending`。
  - `reduce_days` 处罚：基于 `min_retain_days`，动态拦截。
- **营业时间 (升级)**：除了测试“允许”的情形外，**必须测试默认情况下（未开启 `allowOutOfHours`）超出营业时间被拒绝的场景。**

### 三、并发防重与豁免抢占 (冲突检测)
- **多段冲突**：完全重叠、头尾交叠、跨越包围的拦截。
- **首尾相接允许 (新增)**：A 预约 `14:00-15:00`，B 预约 `15:00-16:00` 应当允许。
- **活动状态冲突 (新增)**：与 `active` 状态的订单应当发生冲突。
- **状态豁免**：取消(`cancelled`) 或 **被拒绝(`rejected`)(新增)** 状态不触发冲突。
- **爽约释放抢占**：在开启和**未开启(新增)**抢占释放时的不同边界表现。

### 四、生命周期与状态流转 (Checkin / Checkout) (全新补充)
- **签到边界 (`Check-in`)**：拦截非 `approved` 状态的签到；测试防提前过早签到；验证迟到/爽约等时间判定逻辑。
- **签退计算 (`Check-out`)**：拦截非 `active` 状态的签退；验证正常签退；**验证费用结算、耗材计费逻辑和超时逻辑。**

### 五、修改与撤销规则 (Update / Cancel)
- **取消阈值验证 (修复)**：使用与默认 120 分钟明显不同的自定义 `violation_params_json` 阈值（如 30 分钟），断言在 45 分钟时取消**不会**触发晚取消，以验证自定义规则生效。
- **修改重判规则 (升级)**：修改预约不仅仅是“只能改一次”，**必须测试新时间是否重新触发了冲突校验、超出预约窗口校验、营业时间校验以及修改后的等待审批流转。**

### 六、管理员后门与聚合统计
- **查询与列表 (升级)**：不再只验证 HTTP 200；必须断言返回记录精确匹配、分页/列表筛选参数正确。处理批量参数非法/空数组等边界。
- **副作用拦截与释放 (升级)**：测试管理员审批 (`approve`) / 拒绝 (`reject`) 操作后，资源槽位是否正确释放或锁定；验证物理删除。

## 3. 实施约束
- **严禁修改业务代码**：本阶段唯一目标是编写 `tests/03_reservations.test.ts`。
- **数据隔离**：利用 `beforeEach` 彻底清理表并重置规则。
