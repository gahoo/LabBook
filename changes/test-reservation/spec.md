# Reservation 模块重构与极限测试规范 (Specification)

## 1. 目标与背景
Reservation（预约模块）是系统中最核心、状态流转最复杂的部分。为了在物理剥离代码时不引入任何回归问题，必须遵循严格的 TDD（测试驱动开发）流程。必须消灭所有“绿而不真”的测试，确保覆盖所有深水区边界。

## 2. 测试策略：六大维度极限测试网 (Sprint 1.5 终极硬化版)

### 一、基础参数与边界校验 (`POST /api/reservations`)
- **必填项与格式**：空值、非字符串、字符溢出、非整数的 400 拦截。
- **设备有效性 (新增)**：测试 `equipment_id` 不存在时的 404/400 拦截。隐藏设备的 403 拦截。
- **硬编码强拦截**：导师包含“教授/老师”时的拦截；邮箱后缀白名单拦截。
- **时间极性与边界**：早于当前时间、`end_time <= start_time`、**提前预约天数边界**、**最大时长“恰好等于”边界**的校验。

### 二、设备规则与惩罚降级引擎 
- **时长限制**：`< minDuration` 及单日累计超额拦截。
- **惩罚动态降级**：
  - `REQUIRE_APPROVAL` 处罚：强制将 `auto_approve=true` 预约降级为 `pending`。
- **营业时间**：默认拒绝非营业时间；允许非营业时间预约时的通行。

### 三、并发防重与豁免抢占 (冲突检测)
- **真·并发压测**：使用 `Promise.all` 模拟同时间极速发起的抢占，断言数据库只落入一条记录。
- **多段冲突**：完全重叠、头尾交叠、跨越包围的拦截。首尾相接(`A.end == B.start`)允许。
- **状态豁免**：取消(`cancelled`)、被拒绝(`rejected`) 状态不触发冲突。
- **爽约释放抢占 (恢复)**：测试 `release_noshow_slots` 开启时，超过 30 分钟未签到的 `approved` 订单被后来者抢占的逻辑。

### 四、生命周期与状态流转 (Checkin / Checkout)
- **签到边界 (`Check-in`) (补全)**：
  - **Happy Path**：成功签到后，断言状态准确变更为 `active`，并记录 `actual_start_time`。
  - **异常拦截**：拦截未知 Code、拦截重复签到、拦截非 `approved` 状态的签到、拦截未到签到窗口的过早签到。
- **签退计算 (`Check-out`) (精确化)**：
  - **精准计费**：严格断言具体金额！必须覆盖“按小时计费（涉及向上取整等后端算法）”、“按次计费（Session）”、“固定/免费”，并叠加“耗材费 (`consumable_quantity * consumable_fee`)”的总价断言，绝不能只写 `> 0`。
  - **异常拦截**：拦截未知 Code、拦截重复签退、拦截非 `active` 状态的签退。

### 五、修改与撤销规则 (Update / Cancel)
- **撤销验证 (`Cancel`) (补全)**：
  - 测试未知 Code 的 404 拦截。
  - 分别测试对 `active`（进行中）和 **`completed`（已完成）** 状态订单的取消拦截。
  - 自定义 `lateCancelMinutes` 阈值的精确触发与免罚测试。
- **修改重判 (`Update`) (补全)**：
  - **全量回归拦截**：修改时间必须重新触发“并发冲突”、“超最大时长”、“非营业时间”、“过去时间”的拦截，并断言失败时数据库 `modified_count` 和时间未被篡改。
  - 拦截对非待审批/已审批 (`active/completed/cancelled`) 状态订单的修改。

### 六、管理员后门与聚合统计
- **查询与列表 (补全)**：
  - 批量查询（Batch）：传入空数组、非数组、包含不存在的 Code 时的容错处理。
  - 列表筛选：测试按 `student_name` / `supervisor` / `startDate` 等条件的正确过滤。
- **状态与统计副作用 (补全)**：
  - 测试管理员对非法状态的更新尝试（如不存在的 ID）。
  - 测试统计接口 (`stats`) 在空结果、日期边界下的表现。
  - 测试管理员物理删除订单后，该时间段可被再次预约，且该订单在关联查询中彻底消失。

## 3. 实施约束
- **无条件精确断言**：禁止使用宽泛的 `> 0` 或 `if (res.status === 200)`。
- **验证副作用**：每个核心动作（修改、取消、签到）不仅要验证 HTTP 状态码，必须使用 `SELECT` 去数据库验证核心字段的确切变更。
