# Reservation 模块重构与极限测试规范 (Specification)

## 1. 目标与背景
Reservation（预约模块）是系统中最核心、状态流转最复杂的部分。为了在物理剥离代码时不引入任何回归问题，必须遵循严格的 TDD（测试驱动开发）流程。
在初步完成 28 个测试用例后，我们进一步引入**高可信度测试加固标准**，消除全局数据库污染、时钟依赖等导致的“随机失败”和“虚假覆盖”，确保覆盖所有深水区边界。

## 2. 测试策略：六大维度极限测试网 (Sprint 1.5+ 加固版)

### 零、测试基建加固 (Infrastructure Hardening)
- **P0 测试数据库隔离**：禁用文件并发 (`fileParallelism: false`)，使用专用的 `resetTestDatabase()` 函数在每次测试前清空并重建表结构与默认 settings，防止测试用例间的脏数据污染。
- **P1 全局时钟冻结**：使用 `vi.useFakeTimers()` 固定系统时间。禁止在测试中使用 `Date.now()`，时间必须作为常量或受控变量，以避免测试运行延迟导致边界时间（如 30 分钟迟到判定）失效。
- **P2 前置工厂断言**：封装 `createApproved(eqId, overrides)`，内置对 200 状态码的断言，防止前置数据构造失败导致的后续诡异错误，精确定位报错点。

### 一、基础参数与边界校验 (`POST /api/reservations`)
- **必填项与格式**：空值、非字符串、字符溢出、非整数的 400 拦截。
- **设备有效性**：测试 `equipment_id` 不存在时的 404/400 拦截。隐藏设备的 403 拦截。
- **硬编码强拦截**：导师包含“教授/老师”时的拦截；邮箱后缀白名单拦截。
- **时间极性与边界**：早于当前时间、`end_time <= start_time`、**提前预约天数边界**、**最大时长“恰好等于”边界**的校验、**跨日/时区边界**。

### 二、设备规则与惩罚降级引擎 
- **时长限制**：`< minDuration` 及单日累计超额拦截。
- **惩罚动态降级**：
  - `REQUIRE_APPROVAL` 处罚：强制将 `auto_approve=true` 预约降级为 `pending`。
  - `BAN` 处罚的强拦截。
- **营业时间**：默认拒绝非营业时间；允许非营业时间预约时的通行。

### 三、并发防重与豁免抢占 (冲突检测)
- **P1 真值表区间驱动**：使用 `it.each` 覆盖重叠的核心边界：
  - 完全相同：`[24, 26]` 拦截。
  - 内部子集：`[24.5, 25.5]` 拦截。
  - 左右交叉、跨越包围的拦截。首尾相接(`A.end == B.start`)允许。
  - 不同设备允许重叠；取消/驳回的订单不阻塞新预约。
- **同进程竞争请求**：使用 `Promise.all` 模拟同时间极速发起的抢占，断言数据库只落入一条记录 (JS Event Loop 层面并发)。
- **爽约释放抢占**：测试 `release_noshow_slots` 开启时，超过 30 分钟未签到的 `approved` 订单被后来者抢占的逻辑。必须明确验证**关闭该开关、30分钟内、或已上机时，仍然会阻塞**。

### 四、生命周期与状态流转 (Checkin / Checkout)
- **签到边界 (`Check-in`)**：
  - **Happy Path**：成功签到后，断言状态准确变更为 `active`，并记录 `actual_start_time`。
  - **异常拦截**：提前 30 分钟边界测试、迟到宽限期生成违约记录、拦截 `pending/rejected` 状态的签到。
- **签退计算 (`Check-out`)**：
  - **P1 精准计费**：分离 `session` 与 `fixed` fee 用例。严格断言“按小时计费（涉及 1 分钟与整小时边界向上取整）”、“按次计费”、“固定/免费”，并叠加“耗材费（负数/非法数量拦截）”。
  - **异常拦截**：超时引发违约记录、拦截非 `active` 状态的签退。

### 五、修改与撤销规则 (Update / Cancel)
- **撤销验证 (`Cancel`)**：
  - 测试未知 Code 的 404 拦截。
  - 分别测试对 `active`（进行中）和 **`completed`（已完成）** 状态订单的取消拦截。
  - 自定义 `lateCancelMinutes` 阈值的精确触发与免罚测试。
- **修改重判 (`Update`)**：
  - **P1 强事务验证**：必须刻意制造数据库级别的抛错以验证真 Rollback，或证明在所有前置校验失败时，`modified_count` 未被递增。
  - **全量回归拦截**：修改时间必须重新触发所有时间与冲突拦截。

### 六、管理员后门与聚合统计
- **查询与列表**：
  - 批量查询（Batch）：传入空数组、非数组、超限数据(>200)、重复 code 等容错处理。
  - **P1 严格过滤**：列表筛选必须是“全部条件匹配 (AND)”，测试边界包含非法日期。
- **状态与统计副作用**：
  - 统计接口 (`stats`) 在空结果、日期边界下的健壮性。
  - 物理删除订单后，该时间段可被再次预约，且原订单彻底消失。

## 3. 实施约束
- **无条件精确断言**：禁止使用宽泛的 `> 0` 或 `if (res.status === 200)`。
- **验证副作用**：每个核心动作（修改、取消、签到）不仅要验证 HTTP 状态码，必须使用 `SELECT` 去数据库验证核心字段的确切变更。
