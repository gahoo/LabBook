# 管理员认证与弱密码安全修复 (Security Admin Auth Rework)

## 1. 背景与目标
根据安全审计报告，系统当前存在两个严重的安全漏洞（P0级别）：
1. **管理员明文密码变相泄露**：登录成功后，前端直接将管理员明文密码作为 Token 保存并在每次请求的 `Authorization` 头中明文传输。一旦网络链路被监听或本地缓存泄露，管理员密码将直接被窃取。
2. **默认弱密码风险**：未配置 `ADMIN_PASSWORD` 环境变量时，系统会自动回退使用极不安全的 `admin123`，容易被自动化扫描利用。

本方案旨在合并处理上述两项风险。引入基于 JWT (JSON Web Token) 的标准鉴权，消除明文密作为 Token 传输的风险，同时增强系统启动时的初始凭证容错机制。

## 2. 详细改造方案

### 2.1 消除默认弱密码风险
修改 `server.ts` 中的全局变量初始化：
* 检查环境变量 `ADMIN_PASSWORD`。若存在，直接使用。
* 若不存在，**不再使用**硬编码的 `admin123`。而是改为在进程启动时，通过 `crypto.randomBytes(16).toString('hex')` 动态生成一个 32 字符长度的随机高强度密码。
* 服务端在启动完毕时，通过 `console.warn` 将此动态随机密码打印到控制台，以便系统管理员可以在启动日志中找到初始凭证进行首发登录。

### 2.2 引入 JWT 鉴权体系替换明文 Token
* 引入 `jsonwebtoken` 模块处理会话签发和验签。
* **随机与固定的 `JWT_SECRET` 机制**：
  优先读取环境变量 `process.env.JWT_SECRET`。如果在未配置的情况下，服务端进程启动时同样通过 `crypto.randomBytes` 生成一个专属当前运行周期的临时 Secret。
  *这意味着如果没配置固定的 Secret，每次服务器重启都会使过去签发的 Token 自动作废，起到极大的安全阻断作用。*
* **改造 `/api/admin/login` 接口**：
  * 请求中校验 `password`。符合条件后，不再原样返回密码。而是使用 `jwt.sign` 包装管理员身份信息，签发一个过期时间固定为（`12h`）或（`24h`）的加密 Token 并返回给前端。
* **改造 `adminAuth` 鉴权中间件**：
  * 拦截并截取请求头里面的 `Authorization: Bearer <TOKEN>`。
  * 放弃原先直接判断 `token === adminPassword` 的危险逻辑。
  * 改用 `jwt.verify` 自动校验 JWT 的签名合法性并判断是否超时过期。合法予以放行，篡改或超时则一律阻断（返回 401）。

### 2.3 有关 bcrypt 与时间攻击的调整说明
* 报告中建议的 `bcrypt` 常用于在数据库里持久化存储密码。本项目由于系统非常轻量，管理员密码是通过环境变量（内存变量）挂载的，不涉及落库存储，因此我们在比较用户输入的密码同环境变量时，可以直接使用最基础的比较。
* 虽然直接比较有潜在的时间侧信道攻击风险，但随着使用 JWT，后续所有鉴权请求都是通过 `jsonwebtoken` 自身的校验引擎运作的，该库内置了对签名比对的时间攻击防护。我们不再手动对比明文密码长字符串。

### 2.4 前端改造适配
* 需要观察并微调 `/src/pages/Admin/index.tsx` 和相关 API 工具库涉及登录的回调，确保在 LocalStorage 中存储的是新生成的 `JWT Token`，并将其加入到所有后续请求 Header 的发送携带中。由于目前可能前端逻辑本身是透传鉴权态的，调整幅度极小。
