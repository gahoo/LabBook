## 问题陈述

目前，后台管理系统受到工作流碎片化、逻辑重复和性能瓶颈等问题的困扰。“预约管理”和“报表”模块高度重叠——两者都操作预约数据，但在 UI 上却是完全独立的顶级标签页，包含重复的代码和不同的界面。此外，用于报表的后端 API 严重过载，将简单的列表获取与昂贵的四维数据聚合混合在一起，导致严重的性能问题。同时，“白名单申请”模块也是一个孤立的顶级标签页，导致管理员在进行日常预约管理时无法无缝审查设备访问请求，增加了操作摩擦。最后，预约编辑界面过于臃肿，将基础信息、使用日志和违规记录混合在单一表单中，这就带来了在进行日常信息修正时意外触发违规判定逻辑的风险。

## 解决方案

解决方案是通过整合相关功能并严格隔离管理操作的副作用，从根本上重组管理工作流。“报表”和“白名单申请”将作为顶级标签页被移除。取而代之的是一个“统一预约看板”，它将预约列表和报表指标合并在一起。白名单审批将被上下文感知地嵌入到设备管理视图中，并在新的统一看板上作为一个快速操作横幅呈现。预约编辑抽屉将被拆分为三个完全独立、物理隔离的标签页（预约信息、上机信息、违规记录），以防止产生意外的副作用。在后端，繁重的聚合计算将被提取到一个专用的统计 API 中，所有与违规相关的操作将被统一到一个整洁的 RESTful 命名空间下。

## 用户故事

1. 作为一名管理员，我想要在一个统一的看板中查看预约和报表指标，以便我无需在不同的顶级标签页之间频繁切换上下文。
2. 作为一名管理员，我想要在预约看板顶部看到待审批白名单的快捷审批横幅，以便我能在不打断日常工作流的情况下处理访问请求。
3. 作为一名管理员，我想要待审批的白名单申请能直接显示在设备管理视图中对应设备的下方，以便我能清楚了解用户正在申请哪台设备的权限。
4. 作为一名管理员，我想要独立于使用日志来编辑预约的基础信息（如学生姓名、联系方式），以便我在纠正数据录入错误时不会意外触发迟到或超时违规。
5. 作为一名管理员，我想要系统仅在我明确更新实际上机时间时才自动评估迟到或超时违规，以便惩罚系统保持准确且逻辑上相互隔离。
6. 作为一名管理员，我想要在预约抽屉中有一个专门的区块来管理人工违规，以便我能轻松地添加、编辑或撤销行政处罚。
7. 作为一名管理员，我想要在预约看板上点击“只看未到期”快速筛选按钮，以便我能轻松查看即将到来和当前的预约，而无需手动配置日期范围。
8. 作为一名后端开发者，我想要繁重的统计聚合数据由一个独立的 API 端点提供，以便主预约列表 API 保持轻量化和高性能。
9. 作为一名后端开发者，我想要所有违规相关的端点都归组在一个统一的 RESTful 命名空间下，以便 API 接口表面保持一致且易于维护。

## 实施决策

- 完全从顶部导航栏中移除“报表”和“白名单申请”模块。
- 实施一个“统一预约看板”，提供预约记录列表、时长/费用统计和可视化图表的子视图。
- 增强预约列表 API，使其默认包含报表状态和总费用，但剔除所有的分组和聚合逻辑。
- 创建一个全新的专用统计 API，用于处理所有繁重的分组逻辑（按时间、人员、导师、设备统计使用情况），以为图表和统计视图提供数据。
- 重建预约编辑抽屉，包含三个不同的面板：
  - 面板 1：预约基础元数据。
  - 面板 2：使用执行日志（实际开始/结束时间）。这是唯一一个在保存时会触发系统违规评估的面板。
  - 面板 3：违规记录管理（显示系统违规，并允许对人工违规进行增删改查）。
- 标准化违规的 REST API 命名空间。所有引用 `violation-records` 的遗留路径都将迁移到 `violations` 命名空间。
- 引入一个新的 API 端点，允许修改现有人工违规的违规类型和管理员备注。
- 双端实现白名单申请审批：作为设备管理视图中每个设备下方轻量级的卡片，以及统一预约看板上的内联横幅。
- 明确在设计中排除白名单申请的“全部同意”功能，以防止意外的批量审批。

## 测试决策

- **优秀测试的特征：** 测试应当验证外部行为和状态变化，而不是内部实现细节。例如，通过 API 更新实际上机时间时，应该测试它是否正确地发放或撤销了违规，而不是验证确切的数据库查询结构。
- **统一预约列表：** 验证列表端点是否快速返回基础记录，并正确合并双层状态（审批状态 vs. 报表状态）。
- **统计端点：** 验证新的 `/stats` 端点在给定特定日期范围时，是否能在四个必需的维度上正确聚合数据。
- **隔离的编辑副作用：** 测试对一个预约的三个独立更新操作，确保保存基础元数据不会触发违规评估，而保存使用执行日志时会触发。
- **统一违规命名空间：** 验证通过新的标准化 RESTful 路由创建、更新、撤销和恢复违规是否正确改变了违规状态，并触发了全局的惩罚评估逻辑。
- **现有参考：** 参考代码库中针对独立违规和惩罚规则的现有测试，以确保新的人工违规编辑遵循既定模式。

## 超出范围

- 修改惩罚评估逻辑本身；此次重构仅改变违规触发和管理的位置及方式，不涉及惩罚核心规则。
- 更改面向用户的预约界面或学生申请白名单的流程。
- 为报表统计添加全新的维度或图表（仅迁移现有指标）。

## 补充说明

- 彻底移除白名单申请的“全部同意”按钮是出于特定的用户反馈，即将管理意图和安全性置于单纯的处理速度之上。
