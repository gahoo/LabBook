# 变更规格说明：哨兵逗号查询优化 (Sentinel Comma Optimization)

## 1. 业务背景与合理性分析
在本项目中，`user_penalties` 表的 `contributing_violation_ids` 字段采用了非规范化设计，即存储逗号分隔的 ID 字符串（如 `1,2,3`）。
虽然这违反了数据库第一范式（1NF），但在当前应用规模和场景下具有其合理性：
1. **YAGNI原则**：引入多对多关联表 (`penalty_violations_map`) 会显著增加数据写入、撤销更新逻辑的复杂性，需要事务保证。
2. **读写特征**：该字段主要用于在撤销违规记录时，反查并撤销由于该违规导致的惩罚。读写频率相对较低，不会造成严重的性能瓶颈。

为了弥补这种非规范化设计在模糊匹配时容易出错且代码冗长的问题，我们引入了“哨兵逗号（Sentinel Comma）”模式，即字符串首尾都带有逗号（如 `,1,2,3,`）。

## 2. 现状分析
1. **写入逻辑**：目前后端在自动生成惩罚记录时（`server.ts:643`），已经正确地应用了哨兵逗号写入格式：`const idsStr = \`,\${contributingIds.join(',')},\`;`。
2. **查询/更新逻辑**：在撤销违规记录触发惩罚撤销的代码中（`server.ts:2982`），依然保留着防御性的 4 种条件判断（精确相等、逗号在左、逗号在右、左右皆有）。这是多余且冗长的。

## 3. 方案设计
基于写入口已经统一使用哨兵逗号格式的现状，我们进行以下修改：

### 3.1 精简关联查询条件
* **涉及接口**：`/api/admin/violation-records/:id/:action` (撤销操作)
* **修改动作**：将 4 个 `OR` 连接的匹配条件，精简为单一的 `LIKE '%,id,%'` 匹配。因为 `id` 始终是单个撤销的违规记录 ID，且目标字段前后必然有逗号，所以这个单条件足够严谨，不会发生 `id=1` 匹配到 `id=10` 的情况。
